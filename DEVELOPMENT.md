# Development

## Prerequisites

- Node 22+ and pnpm 10
- Rust 1.88+ (stable) and the [Tauri 2 prerequisites](https://v2.tauri.app/start/prerequisites/) for your OS (WebView2 on Windows, Xcode CLT on macOS, webkit2gtk on Linux)
- Per-platform toolchains (C++ build tools, Xcode, WebKitGTK packages, Android SDK/NDK and Windows Developer Mode, CocoaPods…), exact versions, packaging and signing: **[BUILDING.md](BUILDING.md)**

## Commands

```bash
pnpm install
pnpm stack:up         # the server stack (Docker), needed by the app — see Server below
pnpm dev              # web app on the dev stack (http://localhost:1420; Vite proxies /api)
pnpm build            # typecheck + production web bundle in dist/
pnpm tauri dev        # desktop app with hot reload (VITE_API_ORIGIN=http://localhost:8080 for the dev stack)
pnpm tauri build      # desktop installers (VITE_API_ORIGIN = the public https origin; see src-tauri/tauri.conf.json > bundle)
pnpm android:doctor   # Android toolchain pre-flight (also runs before android:dev / android:apk)
pnpm android:dev      # run on a phone or emulator with hot reload
pnpm android:apk      # debug APK — release and signing: BUILDING.md
pnpm ios:doctor       # iOS pre-flight (macOS only)
pnpm ios:dev          # run on a simulator or an iPhone with hot reload
pnpm test             # vitest: projects app (jsdom), domain, contracts, providers, server (Node)
pnpm check            # typecheck + lint + format:check + knip + test + prefill freshness
pnpm rust:check       # cargo fmt --check + clippy + cargo test
```

## Server

The app runs on accounts and a server ([ADR 0001](docs/adr/0001-backend-accounts-platform-keys.md), design [`docs/superpowers/specs/2026-10-11-backend-queue-accounts-design.md`](docs/superpowers/specs/2026-10-11-backend-queue-accounts-design.md), plans in `docs/superpowers/plans/`; phase 2: [plan](docs/superpowers/plans/2026-10-12-backend-phase-2.md); phase 3: [plan](docs/superpowers/plans/2026-10-12-backend-phase-3.md)). Phases 1 to 3 are in the repository: accounts, listings, uploads and object storage behind a REST API; credits; photo-pack and listing-copy runs queued with BullMQ and generated by a worker that holds the platform's provider keys; live progress over SSE. The web and desktop/phone apps run on it (ARCHITECTURE.md); the local-first release is on the `byok` branch. Conventions: the `backend` skill.

Prerequisites: Docker (Desktop on Windows/macOS). Then:

```bash
pnpm stack:up            # creates ./secrets once (random, git-ignored), builds and starts the stack, waits until healthy
pnpm smoke:server        # end-to-end check: sign-up → email → upload → thumbnail → account deletion
pnpm stack:down
pnpm test:integration    # server tests against Postgres, Redis and SeaweedFS started by Testcontainers
pnpm --filter @aiv/server build        # esbuild bundle in apps/server/dist (api.js, migrate.js)
pnpm --filter @aiv/server db:generate  # SQL migration from src/db/schema.ts into apps/server/drizzle (commit it, never edit it)
pnpm --filter @aiv/server auth:schema  # regenerate Better Auth's tables (src/db/auth-schema.ts) after changing its plugins
```

Real providers locally: `pnpm stack:up:cloudflare` runs the dev stack on Cloudflare Workers AI (photos FLUX.2 [klein] 4B, texts Llama 4 Scout) instead of the Mock providers — put `CLOUDFLARE_ACCOUNT_ID` (32 hex characters, not a secret) in `.env` and your Workers-AI-only API token in `./secrets/cloudflare_api_token`; `scripts/check-cloudflare-env.mjs` says what is missing. It spends your Cloudflare free allowance (about 110 neurons per photo of 10,000 a day). `compose.cloudflare.yaml` is the override.

Running the app: `pnpm stack:up`, then `pnpm dev` (web; in Git Bash `VITE_API_ORIGIN` must not be set to `/` by hand — MSYS rewrites it — leave it unset, `/` is the default) or `VITE_API_ORIGIN=http://localhost:8080 pnpm tauri dev` (desktop). `pnpm tauri dev|build` (`scripts/tauri.mjs`) first writes the git-ignored `src-tauri/capabilities/api.json` (HTTP to `<origin>/api/*` only) and the CSP patch `src-tauri/tauri.api.conf.json`, and refuses to run without `VITE_API_ORIGIN`; a release uses the public `https://` origin. On the web, Vite proxies `/api` to the stack (`API_PROXY_TARGET`, default `http://localhost:8080`) and presents the stack's origin, so cookies and the api's CSRF check behave as behind Caddy; `compose.dev.yaml` also trusts `http://localhost:1420` (Tauri dev webview). Emails (verification, reset, deletion) arrive in Mailpit and their links open the stack's web app on :8080. Sign-up is rate-limited to 5 per hour per IP: repeated test runs clear the dev stack's `rl:auth:*` Redis keys. The desktop app keeps the session token in the OS keychain (`session_token`; memory only on phones until the keystore lands), the web app uses httpOnly cookies.

Production on one VPS (phase 4: [plan](docs/superpowers/plans/2026-10-12-backend-phase-4.md)): put `PUBLIC_ORIGIN`, `MAIL_FROM` and `CADDY_SITE` (the public host, for automatic HTTPS) in a `.env` next to `compose.yaml`, write real secrets into `./secrets` (a real Resend key in `resend_api_key`), also `AIV_VERSION` (the released version: `compose.yaml` pulls `ghcr.io/tropi83/aiv-server:<version>` and `aiv-web:<version>` and refuses to start without it), then `docker compose pull && docker compose up -d --wait`. Every service rotates its logs (10 MB × 5) and has a memory limit sized for 4 vCPU / 8 GB; `pnpm stack:up` builds locally instead (`compose.dev.yaml` + `deploy/dev.env`). `GET /api/v1/ready` also answers 503 `worker` when no worker has beaten for 60 s (heartbeats in the Redis sorted set `worker:heartbeats`), which is what the outside uptime check watches. `scripts/check-compose.mjs` (CI) enforces pinned images, log rotation, memory limits, no Mock provider and provider keys on the worker only.

## Mobile image import

`features/workspace/useImageImport.ts#pickImageFile(source)` picks the mechanism per platform (verified against `tauri-plugin-dialog` 2.7 / `tauri-plugin-fs` 2.5 sources):

- `gallery` — `open({ pickerMode: "image", filters })`: PHPicker on iOS, the media picker (`ACTION_GET_CONTENT`, `image/*`) on Android. The result is a `content://` or `file://` URI; `readFile(uri)` resolves it through the mobile plugin (no fs scope entry needed — URL paths bypass the path scope by design). Opaque media ids become `photo.jpg`.
- `camera` — a hidden `<input type="file" accept="image/*" capture="environment">`: wry's Android `RustWebChromeClient.onShowFileChooser` honours `capture` and hands the shot to the camera app with `ACTION_IMAGE_CAPTURE` (output file through the `${applicationId}.fileprovider` FileProvider); WKWebView opens the camera directly. wry checks `resolveActivity()` first, and since Android 11 other apps are hidden from it unless declared, so the manifest declares `<queries><intent><action android:name="android.media.action.IMAGE_CAPTURE"/></intent></queries>` — without it the check fails, wry logs "Media capture intent could not be launched" and opens the gallery (verified on Android 12, 2026-09-12). No `CAMERA` permission is declared on purpose: wry only asks for it when the manifest declares it, and the camera app takes the picture. Falls back to the plain file input on the web.
- `files` / `auto` — desktop dialog or `<input type=file>`; `auto` becomes `gallery` on mobile.

There is no official Tauri camera plugin (only a barcode scanner), which is why the camera path relies on the WebView's file chooser.

## Cloudflare Workers AI notes (the worker's image provider)

Verified 2026-09-12 against https://developers.cloudflare.com/workers-ai/ (model pages, launch changelogs, REST API, pricing, limits, error codes) and the model JSON schemas in `cloudflare/cloudflare-docs`.

- REST: `POST https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/run/{model}` with `Authorization: Bearer <token>`. Errors use the v4 envelope `{ success:false, errors:[{code,message}] }`: bad token = 400/401 code 9106/10000, bad account id = 404 code 7003, **5018 = account not allowed for a private model**, **3030 = invalid model input** (e.g. the model has no image tensor) — but also FLUX's output safety filter: `AiError: Your output has been flagged. Please choose another prompt / input image combination` (seen 2026-09-12 on plain shoe product shots, a false positive; not listed on the errors page). `classifyRejectedInput()` therefore reads the message, content filter first: an output flag is `CONTENT_REJECTED` and retryable, and every retry sends a different seed (`seedForAttempt`; a manual Retry draws a new one) because FLUX returns the same image for the same seed. 3036 = daily neurons exhausted (429).
- **FLUX.2 [klein]** (`@cf/black-forest-labs/flux-2-klein-4b`, `-9b`): `multipart/form-data` with `prompt`, `input_image_0..3` (PNG/JPEG, "smaller than 512×512"), `width`/`height` 256–1920, `seed`, `guidance`; steps fixed at 4. Answer: JSON envelope with `result.image` (base64). Pricing 4B: $0.000059 per input tile + $0.000287 per output 512×512 tile ⇒ ≈110 neurons per 1K image.
- **Stable Diffusion 1.5 img2img**: JSON body `prompt`, `image_b64`, `width/height` 256–2048, `num_steps` ≤ 20, `strength`, `guidance`, `negative_prompt`, `seed`; answer = raw PNG bytes. SDXL base/lightning and DreamShaper are _not_ img2img despite the shared schema (3030).
- Model availability: `GET /accounts/{id}/ai/models/search?task=Text-to-Image`; catalogue entries missing from the list are reported unavailable.
- **No CORS** on `api.cloudflare.com` (OPTIONS → 405): only the server's worker calls it (direct mode). Host allowlist: `ALLOWED_HOSTS` in `packages/providers/src/http.ts`.
- Credentials: `CLOUDFLARE_ACCOUNT_ID` and the Docker secret `cloudflare_api_token`, mounted in the worker only (`apps/server/src/worker/registry.ts`).
- Catalogue and option specs: `packages/providers/src/cloudflare/CloudflareModels.ts`.

## Gemini API notes (the worker's text provider)

- **Checked 2026-10-12** (models, deprecations, pricing, rate limits, Interactions overview): the Interactions API is generally available and recommended, `store` is still a request field (`store: false` cannot run in the background). Text models in the catalogue are current; `gemini-3.1-flash-lite` shuts down on 2027-05-07 (replacement `gemini-3.5-flash-lite`). `gemini-2.5-flash-image`: Google's pricing page says shut down on 2026-10-02, its deprecations page says 2027-03-15 — kept in the (disabled) catalogue, to resolve before Gemini image generation is re-enabled; newer image models exist (`gemini-nano-banana-2.1`). Free-tier RPM/RPD per model are only shown in AI Studio, not in the docs. Cloudflare (same day): FLUX.2 [klein] 4B costs 26.05 neurons per output 512×512 tile and 5.37 per input tile (≈ 104 + 5 neurons for a 1K image with a 512 px reference); 10,000 free neurons per day reset at 00:00 UTC; $0.011 per 1,000 neurons beyond. The adapters live in `packages/providers` (shared with the server worker).
- **Listing copy** (`GeminiListingCopy.ts`): Interactions API with `system_instruction` + text + image parts, `store: false`. Catalogue `GEMINI_TEXT_MODELS` (cheapest first, USD per 1M tokens, ai.google.dev/gemini-api/docs/pricing checked 2026-09-13): 3.1 Flash-Lite 0.25/1.50 (default), 3.5 Flash-Lite 0.30/2.50, 2.5 Flash 0.30/2.50, 3.6 Flash 0.75/3.75 — all with a free tier. The user's choice lives in `settings.copyModelByProvider`; unknown ids fall back to the default (`resolveCopyModel`). `gemini-2.5-flash-lite` was removed on 2026-09-13: still documented by Google but the live API answers 404 "no longer available to new users".
- **Image generation with Gemini is not the platform's default**: the worker generates images with the provider in `IMAGE_PROVIDER` (Cloudflare by default); `GeminiProvider` and its tests remain in `@aiv/providers`.
- Image generation/editing uses the **Interactions API** (`POST /v1beta/interactions`). Models: `gemini-3.1-flash-image` (default, 512px–4K), `gemini-3.1-flash-lite-image` (1K only), `gemini-3-pro-image` (1K–4K), `gemini-2.5-flash-image` (legacy, no `image_size`). Capabilities are centralized in `packages/providers/src/gemini/GeminiModels.ts` — update that file when Google changes models.
- Billing: image models have **no free tier** in the Gemini API (pricing, 2026-09-11). Free-tier projects get `limit: 0` on `generate_content_free_tier_requests` → `FREE_TIER_NO_ACCESS`. The platform's Gemini key must belong to a project with billing for image models.
- API keys: new AI Studio keys are _authorization keys_; unrestricted legacy standard keys are rejected by Google (full rejection of standard keys announced for September 2026).
- 429 handling relies on `error.details` (`QuotaFailure` with `quotaId`/`quotaValue`/`quotaDimensions.model`, `RetryInfo.retryDelay`). Per-minute ids contain `PerMinute`, daily ids `PerDay`; `quotaValue: "0"` means the model is not part of the plan (enable billing / Tier 1). Usage is counted locally (`usage-tracker.ts`) because the Gemini API has no consumption endpoint for API keys; daily counters reset at midnight Pacific like Google's.
- Rate limits/quotas depend on the project tier. The queue treats `429` as retryable and honours `Retry-After`; quota exhaustion (`QUOTA_EXCEEDED`) is not retried.

## Vinted pre-fill (desktop)

Flow: `PostButton` → `publish-store` → `PublishBridge` (`TauriVintedBridge` → `vinted_*` commands in `src-tauri/src/vinted.rs`) → a second `WebviewWindow` on vinted.com into which Rust evaluates the pre-fill script. vinted.com gets no Tauri IPC (no capability targets the `vinted` window). Security rationale: SECURITY.md → "Vinted window".

- **Script**: `src/infrastructure/publish/vinted/{prefill,selectors,entry}.ts`, bundled into `src-tauri/scripts/vinted-prefill.js` by `pnpm build:prefill` (Vite library build, IIFE) and compiled into the binary with `include_str!`. The generated file is committed; `pnpm prefill:verify` (part of `pnpm check` and CI) rebuilds it and fails when the committed copy is stale. That directory may only `import type` from `@aiv/domain/services/publish` — nothing from the app exists inside vinted.com.
- **Selectors**: every DOM anchor lives in `selectors.ts` as ordered candidate lists (first match wins). Checked against the live mobile web form on 2026-09-13 (`title--input`, `description--input`, `add-photos-input`, `image-wrapper-N` — the media grid sits outside the `<form>`, so thumbnails are counted on the whole document). When Vinted changes its form, update that file (specific anchors first, generic fallbacks last), bump its "verified on" date, run `pnpm build:prefill` and commit both files.
- **The window**: one `Window` with two child webviews (Tauri `unstable` feature): `vinted-bar` on top (44 px, `public/vinted-bar.{html,css,js}`, an app page with no capability; Rust pushes the localized guidance from `src/app/publish-bar.ts` through `vinted_status` → `eval`) and `vinted` below (vinted.com). `layout()` re-fits both on resize / scale change.
- **When it runs**: by itself, as soon as the window is on `/items/new` — after a page load (`vinted:page`) or a client-side navigation (Vinted's own “Sell” entry; caught by the 500 ms location poll of `vinted_poll`) — and again when the document was replaced (reload). The panel's _Fill again_ button re-runs it by hand. The script waits up to 10 s for the form to render (`status` stays `null` meanwhile) before reporting `pageOk: false`.
- **What the script does**: attaches the photos through the hidden file input, then mounts a paste icon (Lucide clipboard-paste, inlined) inside `.web_ui__Input__content` of the title and of the description; the text is written — React-style, through the prototype setter + `input`/`change` events — only when the user taps the icon. Status per field: `ready` → `filled` (or `not_found` / `failed`). It never clicks “Add”.
- **Inspecting the live form**: in `pnpm tauri dev`, right-click → _Inspect_ inside the Vinted window (devtools exist in debug builds only), open the sell form and run:

  ```js
  JSON.stringify(
    [...document.querySelectorAll("input, textarea")].map((e) => ({
      tag: e.tagName,
      name: e.name,
      id: e.id,
      type: e.type,
      testid: e.dataset.testid,
      accept: e.accept,
    })),
  );
  ```

  then, after attaching a photo by hand, look for the thumbnail anchor (`[data-testid*="thumbnail"]`, `img[src^="blob:"]`).

- **Manual checklist** (any change to the flow): log in (email, then a social login) and restart the app — the session persists; Post → reach the form through Vinted's own “Sell” entry (no page load) and, in a second run, through _Open the sell form_: both times the photos attach by themselves and the report shows title and description `ready`, then `filled` after tapping the icons in Vinted, with `attached === requested`; the status bar above Vinted says the same at each step (login → sell form → filling → Photos n/n · Title ⧉ · Description ⧉ → ✓) and survives a window resize; reloading the form (F5) fills it again; nothing is published without clicking Vinted's “Add”; closing the Vinted window mid-flow brings the workspace back with “The Vinted window was closed.”; Settings → Publishing → _Log out of Vinted_ erases the session (the next open asks to log in); closing the main window also closes the Vinted window; the web build shows the button disabled with “Available in the desktop app.”.

## Adding a provider

Providers run in the server's worker only.

1. Implement the adapter in `packages/providers/src/<id>/` (models catalogue, request mapper, error mapper to `GenerationErrorCode`) with its tests.
2. Register it in `apps/server/src/worker/registry.ts` and `apps/server/src/providers/catalogue.ts` (models, neuron/token estimates).
3. Add its hosts to `ALLOWED_HOSTS` (`packages/providers/src/http.ts`).
4. Its key is a Docker secret mounted in the `worker` service only (`compose.yaml`), read through `*_FILE` in the worker config; `scripts/check-compose.mjs` must still pass. Document it in SECURITY.md and PRIVACY.md (sub-processor).
