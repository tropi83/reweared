# Backend phase 1 — compose stack, API: accounts, listings, uploads, object storage — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Resuming?** Read the "Progress" section at the bottom first: it says which tasks are done (with commits) and any deviation from the text below. Read the `backend` skill before any task.

**Goal:** A `docker compose up` stack where a person can **sign up, verify their email, sign in (cookie or bearer), create a listing, upload a photo and get its thumbnail back** — all through the API, with every invariant of the design that applies to this phase tested. No generation, no credits, no client change (those are phases 2 and 3).

**Architecture:** `apps/server` (Fastify 5, one image; phase 1 only ships the `api` and `migrate` entrypoints — the `worker` arrives in phase 2) talks to Postgres (drizzle) for accounts, listings, image metadata, settings and recipes; to an S3-compatible object store for image bytes; to Redis for rate limits. Better Auth handles accounts and sessions. `packages/contracts` holds the zod schemas shared with the clients. Caddy is the only public entry and serves the web bundle and `/api`.

**Tech Stack (registry versions checked 2026-10-11 with `pnpm view`):** fastify 5.12 · better-auth 1.7 (drizzle adapter, bearer plugin) · drizzle-orm 0.45 + drizzle-kit 0.31 + pg 8.23 · zod 4.6 + fastify-type-provider-zod 7 · @fastify/multipart 10 · @fastify/rate-limit 11 · ioredis 6 · @aws-sdk/client-s3 3.x · sharp 0.35 · pino 10 · resend 6 · nodemailer 10 (dev SMTP to Mailpit) · testcontainers 12.2 (+ `@testcontainers/postgresql`, `@testcontainers/redis`) · esbuild 0.28 (server bundle) · tsx 4 (dev). Pin exact versions in task 2 with `pnpm add`, after reading each project's current docs for the APIs used.

**Spec:** `docs/superpowers/specs/2026-10-11-backend-queue-accounts-design.md` (§1 topology, §3 data model, §6 API, §7 security) — amended by task 1 for the decisions below.

- **The client does not change** (`src/`, `src-tauri/`): no import of `apps/server`, no new host in `ALLOWED_HOSTS` / CSP / Tauri scope. That is phase 3.
- Every route validates its input with zod (`packages/contracts`), answers errors as `{ code, message }` with a `GenerationErrorCode` or an HTTP-level code (`UNAUTHENTICATED`, `NOT_FOUND`, `VALIDATION_FAILED`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `RATE_LIMITED`), never a stack trace.
- **Every data access takes the session user** (`ctx.user.id`), never a user id from the request; another user's resource answers **404**.
- Ids: `createId()` / `assertSafeId()` from `@aiv/domain/lib/ids` for listings, images and recipes (Better Auth keeps its own user/session ids). Object keys: `u/<userId>/l/<listingId>/<bucket>/<assetId>.<ext>`; the user id is checked against `^[A-Za-z0-9_-]{1,64}$` before building a key.
- No secret in the repo, the image, `.env` or logs: secrets are files under `secrets/` (git-ignored) mounted as Docker secrets; config reads `X_FILE` → file contents, falling back to `X` only in tests.
- Logging: pino JSON, redaction of `authorization`, `cookie`, `set-cookie`, `set-auth-token` headers, request bodies never logged, plus the shared `redact()` patterns. Never log emails in full, prompts, images, tokens or verification URLs.
- Windows shell note: the Bash tool corrupts long heredocs and single quotes inside `node -e` — write files with the Write tool, run multi-line scripts from the scratchpad.

## Decisions taken in this plan (beyond the spec)

1. **SeaweedFS replaces MinIO.** MinIO stopped publishing Community Edition images and binaries in October 2025 and its repository was marked unmaintained in 2026; `minio/minio:latest` gets no security fixes. The server only speaks the S3 API (`@aws-sdk/client-s3`, `forcePathStyle: true`), so the store is swappable: **SeaweedFS** (Apache-2.0, single `weed` binary with an S3 gateway) in dev, CI and the default compose; a managed S3 (Hetzner / Scaleway / OVH Object Storage) stays possible in phase 4 by changing the endpoint. Garage (AGPL) and RustFS (young) were the other candidates. Pin the SeaweedFS image tag after checking its releases in task 8. **Confirmed by the owner on 2026-10-11.**
2. **Images are streamed by the API, not redirected to presigned URLs.** A presigned URL must be signed for the host the browser uses; with the store on the internal network that means a public storage hostname or a signed path rewrite in Caddy. Streaming `GET /images/:id` through the api keeps the bucket fully private, keeps authorization in one place and is cheap at this scale (thumbnails are ~30 KB). `Cache-Control: private, max-age=31536000, immutable` + `ETag` (assets are immutable). Presigned URLs can come back behind the same route if bandwidth ever matters.
3. **Password hashing = Better Auth's default (scrypt).** OWASP lists scrypt as acceptable; argon2id would need a native module (`@node-rs/argon2`) and custom `hash`/`verify` hooks for no material gain. The spec's "argon2id" becomes "Better Auth default (scrypt)".
4. **The root stays the web app** (phase 0 decision 1 confirmed): `apps/server` and `packages/contracts` join the workspace, no `apps/web` move.
5. **Email**: a `Mailer` interface with `ResendMailer` (production), `SmtpMailer` (dev → Mailpit through nodemailer) and `MemoryMailer` (tests). Resend's SDK cannot target Mailpit, hence SMTP in dev.
6. **BMP is refused server-side** (`UNSUPPORTED_MEDIA_TYPE`): sharp cannot decode it. GIF/AVIF are re-encoded to PNG like the client does; the phase 3 client converts BMP before upload.
7. **Export ZIP (`GET /listings/:id/export`) moves to phase 3** with the client switch (the client already builds ZIPs).
8. **Redis in phase 1** only backs rate limits (`@fastify/rate-limit` store) and Better Auth's rate limiter; queues arrive in phase 2.
9. **Two shared helpers move to `@aiv/domain/lib`**: `redact` (+ patterns) from `src/lib/logger.ts`, and `sniffMimeType` from `src/infrastructure/image/image-processing.ts` (pure byte checks) — so client and server cannot drift.

### Task 7: Image upload and delivery

**Files:** `apps/server/src/images/{process-upload.ts,process-upload.test.ts,routes.ts}`, `apps/server/test/fixtures/*` (generated in the test with sharp, no binary fixture with personal metadata), `apps/server/test/images.int.test.ts`.
